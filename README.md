# Repair Service MVP 🔧

Backend MVP-система для управления заявками на ремонт техники.

Проект реализован на **FastAPI** и предназначен для автоматизации процесса обработки заявок: от создания обращения клиента до диагностики, ремонта и выдачи результата.

---

🚀 Возможности

# Клиент

* Проверка статуса заявки по ID.
* Получение информации о текущем этапе ремонта.
* Получение контактов оператора.

### Оператор

* Создание новых заявок. Клиент определяется по телефону: повторное обращение попадает к тому же клиенту, а если телефон уже есть с другими ФИО или email, вернётся 400 с данными существующего клиента.
* Просмотр списка заявок.
* Список клиентов с поиском по ФИО или цифрам телефона (`/operator/clients?search=`) и история обращений клиента (`/operator/clients/{id}/applications`).
* Удаление заявок.
* Выдача устройства клиенту (`/operator/{id}/issue`) после пройденной проверки, после этого заявка закрыта.
* Снятие исполнителя с заявки, если он не может её выполнить (`/operator/{id}/release`): на диагностике и проверке снимается инженер, на ремонте мастер.

### Инженер

* Просмотр всех заявок.
* Бронирование заявки в диагностику (`/engineer/{id}/takeEngineer`): одну заявку может взять только один инженер.
* Отметка о завершении диагностики с результатом в теле запроса `{"diagnostic_info": "..."}`: только инженер, который забронировал заявку.
* Отказ от забронированной заявки на диагностике или проверке (`/engineer/{id}/release`).
* Проверка ремонта (`/engineer/{id}/check`, тело `{"passed": true}` или `{"passed": false, "comment": "что не так"}`): только инженер заявки. Пройдена — устройство готово к выдаче, не пройдена — заявка возвращается на повторную диагностику, брони снимаются, списанные запчасти остаются.

### Мастер по ремонту

* Просмотр заявок.
* Взятие заявки в работу после диагностики (`/repairer/{id}/takeRepair`).
* Отметка о завершении ремонтных работ: только мастер, который взял заявку.
* Отказ от взятой заявки до завершения ремонта (`/repairer/{id}/release`), списанные запчасти остаются в заявке.
* Просмотр склада запчастей с поиском по названию.
* Списание запчастей со склада на заявку (название + количество, цена берётся со склада); удаление возвращает их на склад.
* Запчасти можно менять только после диагностики, до завершения ремонта и только в своей заявке.
* Автоматический расчёт стоимости: запчасти + фиксированная стоимость работы (5000).

### Администратор

* Просмотр всех заявок.
* Управление кодами доступа сотрудников.
* Создание базы данных.
* Деактивация сотрудников: токен уволенного перестаёт работать сразу, а не через 24 часа.
* Склад запчастей: добавление позиций, изменение цен и остатков.

## ⚙️ Настройка базы данных

> Alembic пока нет. Новую пустую БД создаёт `POST /services/database_create` (**удаляет все данные**). Существующую БД обновлять без потери данных SQL-миграциями из папки `migrations/`, их можно запускать повторно:
>
> ```bash
> psql "postgresql://user:password@localhost:5432/database" -v ON_ERROR_STOP=1 -1 -f migrations/001_clients_and_check.sql
> ```

Строка подключения к БД хранится в `.env` (не коммитится в git) и подхватывается через `pydantic-settings`.

Скопировать пример конфига и подставить свои данные:

```bash
cp .env.example .env
```

```
DATABASE_URL=postgresql://user:password@localhost:5432/database
```

# 🔐 Авторизация

В проекте используется JWT-аутентификация.

Сотрудники получают уникальный код доступа, который хранится в базе данных в виде SHA-256 хеша.

Вход в Swagger: кнопка **Authorize**, код доступа ввести в поле `username`, поле `password` оставить пустым.

После входа пользователь получает JWT-токен:

```
Authorization: Bearer <token>
```

## 📊 Основные сущности

### Application

Заявка клиента:

* клиент (`client_id`); ФИО, телефон и email в ответах API берутся из клиента
* описание проблемы
* статус ремонта
* этап выполнения (`status_info`): 0 — создана, 1 — диагностика завершена, 2 — ремонт завершён, 3 — проверка пройдена, 4 — выдана клиенту
* результат диагностики и комментарий последней проверки (`check_result`)
* инженер, забронировавший заявку (assignee_engineer_id), и мастер, взявший её в ремонт (assignee_repairer_id)
* список запчастей, стоимость запчастей, стоимость работы и итоговая стоимость

---

### Client

Клиент сервисного центра, один на телефон:

* ФИО
* телефон (уникальный)
* email
* все его заявки

---

### StockPart

Позиция на общем складе (ведёт админ):

* название (уникальное)
* цена
* остаток

---

### Part

Запчасть, списанная со склада на заявку:

* привязка к заявке и к позиции склада
* название и цена на момент списания (изменение цены на складе не меняет уже идущие ремонты)
* количество

---

### AccessCode

Данные доступа сотрудников:

* ФИО
* роль
* хеш кода
* активность аккаунта

## 🔄 Жизненный цикл заявки

```
Создание заявки
        |
        v
Ожидание диагностики
        |
        v
Взята в диагностику (инженер)
        |
        v
Диагностика завершена
        |
        v
Взята в работу (мастер)
        |
        v
Ремонт выполнен
        |
        v
Проверка (инженер заявки) ---- не пройдена ----> Ожидание повторной диагностики
        |
        v
Проверка пройдена
        |
        v
Выдано клиенту (оператор), заявка закрыта
```

До завершения своего этапа инженер или мастер может отказаться от заявки, а оператор может снять исполнителя. Тогда заявка возвращается на ожидание своего этапа, и её берёт другой сотрудник.

## ✅ Тесты

```bash
python -m pytest
```

Тесты используют отдельную SQLite-базу в памяти, рабочую БД из `.env` не трогают.

Прогнать те же тесты на PostgreSQL можно через `TEST_DATABASE_URL`. Указывать **только отдельную пустую БД**: тесты удаляют в ней все таблицы.

```bash
TEST_DATABASE_URL=postgresql://user:password@localhost:5432/repair_test python -m pytest
```
