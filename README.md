# Repair Service 🔧

Backend MVP-система для управления заявками на ремонт техники.

Проект реализован на **FastAPI** и предназначен для автоматизации процесса обработки заявок: от создания обращения клиента до диагностики, ремонта и выдачи результата.

---

🚀 Возможности

# Клиент

* Регистрация и вход по логину и паролю (`/auth/client/register`, `/auth/client/login`).
* Активация кабинета после обращения к оператору: регистрация с тем же телефоном, ФИО, email и кодом своей заявки добавляет логин и пароль к существующему клиенту. Все его старые заявки сразу доступны в кабинете.
* Создание онлайн-заявки (`POST /client/applications`): описание, устройство, модель, адрес и удобные дата/время встречи с курьером (`courier_visit_at`). ФИО и телефон берутся из аккаунта. В ответе код заявки, источник и статус доставки.
* Список своих заявок (`GET /client/applications`): id, код, описание, устройство, модель, время создания, источник онлайн/офлайн, время встречи, доставка, статус и этап (`status_info`). Новые сверху; видны и онлайн-заявки, и заявки оператора.
* Проверка статуса заявки после входа по коду (`/client/status?application_code=`).
* Получение информации о текущем этапе ремонта.
* Получение контактов оператора.

### Оператор

* Создание новых заявок с обязательными полями `device`, `device_model` и `address` (адрес клиента). Время создания заявки (`created_at`) проставляется автоматически. Клиент определяется по телефону: повторное обращение попадает к тому же клиенту, а если телефон уже есть с другими ФИО или email, вернётся 400 с данными существующего клиента.
* Просмотр списка заявок.
* Управление доставкой онлайн-заявок (`POST /operator/{id}/delivery`): курьер выехал → забрал посылку → посылка прибыла в центр. Очередь курьера по времени встречи: `GET /operator/deliveries`.
* Список клиентов с поиском по ФИО или цифрам телефона (`/operator/clients?search=`) и история обращений клиента (`/operator/clients/{id}/applications`).
* Удаление заявок.
* Выдача устройства клиенту (`/operator/{id}/issue`) после пройденной проверки, после этого заявка закрыта.
* Снятие исполнителя с заявки, если он не может её выполнить (`/operator/{id}/release`): на диагностике и проверке снимается инженер, на ремонте мастер.

### Инженер

* Просмотр всех заявок.
* Бронирование заявки в диагностику (`/engineer/{id}/takeEngineer`): одну заявку может взять только один инженер.
* Отметка о завершении диагностики с результатом в теле запроса `{"diagnostic_info": "..."}`: только инженер, который забронировал заявку.
* Отказ от забронированной заявки на диагностике или проверке (`/engineer/{id}/release`).
* Проверка ремонта (`/engineer/{id}/check`, тело `{"passed": true}` или `{"passed": false, "comment": "что не так"}`): только инженер заявки. Пройдена — устройство готово к выдаче, не пройдена — заявка возвращается на повторную диагностику, брони снимаются, списанные запчасти остаются.

### Мастер по ремонту

* Просмотр заявок.
* Взятие заявки в работу после диагностики (`/repairer/{id}/takeRepair`).
* Отметка о завершении ремонтных работ: только мастер, который взял заявку.
* Отказ от взятой заявки до завершения ремонта (`/repairer/{id}/release`), списанные запчасти остаются в заявке.
* Просмотр склада запчастей с поиском по названию.
* Списание запчастей со склада на заявку (название + количество, цена берётся со склада); удаление возвращает их на склад.
* Запчасти можно менять только после диагностики, до завершения ремонта и только в своей заявке.
* Автоматический расчёт стоимости: запчасти + фиксированная стоимость работы (6000 ₽ для онлайн-заявок, 5000 ₽ для офлайн). Старые заявки с неизвестным источником сохраняют тариф 5000 ₽.

### Администратор

* Просмотр всех заявок.
* Управление кодами доступа сотрудников.
* Создание базы данных.
* Деактивация сотрудников: токен уволенного перестаёт работать сразу, а не через 24 часа.
* Склад запчастей: добавление позиций, изменение цен и остатков.

## ⚙️ Настройка базы данных

> Alembic пока нет. Новую пустую БД создаёт `POST /services/database_create` (**удаляет все данные**). Существующую БД обновлять без потери данных SQL-миграциями из папки `migrations`, их можно запускать повторно:
>
> ```bash
> psql "postgresql://user:password@localhost:5432/database" -v ON_ERROR_STOP=1 -1 -f backend/migrations/001_clients_and_check.sql
> psql "postgresql://user:password@localhost:5432/database" -v ON_ERROR_STOP=1 -1 -f backend/migrations/002_client_accounts_and_codes.sql
> psql "postgresql://user:password@localhost:5432/database" -v ON_ERROR_STOP=1 -1 -f backend/migrations/003_application_address_and_time.sql
> psql "postgresql://user:password@localhost:5432/database" -v ON_ERROR_STOP=1 -1 -f backend/migrations/004_application_delivery.sql
> ```
>
> `001` — клиенты, этап проверки ремонта, склад и брони; `002` — аккаунты и сессии клиентов, устройство и код заявки (старым заявкам код генерируется автоматически); `003` — адрес и время создания заявки (у старых заявок адрес «не указан», время — момент миграции); `004` — источник и удобное время встречи с курьером. У старых заявок источник `unknown` («Не указан»), поскольку раньше он не сохранялся; их статусы не меняются. Запускать по порядку.

Строка подключения к БД хранится в `backend/.env` (не коммитится в git) и подхватывается через `pydantic-settings`.

Скопировать пример конфига и подставить свои данные:

```bash

```

# 🔐 Авторизация

В проекте используется JWT-аутентификация.

Сотрудники получают уникальный код доступа, который хранится в базе данных в виде SHA-256 хеша.

Вход в Swagger: кнопка **Authorize**, код доступа ввести в поле `username`, поле `password` оставить пустым.

После входа пользователь получает JWT-токен:

```
Authorization: Bearer <token>
```

### Один кабинет для заявок оператора и сайта

Телефон определяет одну карточку клиента. Вход в кабинет по-прежнему выполняется по логину и паролю; персональные данные сами по себе не дают доступ к истории.

1. **Первое обращение к оператору.** Оператор создаёт заявку через `POST /operator/add_application` и передаёт клиенту `code` из ответа. Дома клиент вызывает `POST /auth/client/register`, указав свои данные, новый логин, пароль и `application_code`. Существующая карточка получает доступ в кабинет, её `id` и все заявки сохраняются.
2. **Первое обращение онлайн.** Клиент регистрируется без `application_code`, входит через `/auth/client/login` и создаёт заявки через `/client/applications`.
3. **Повторное обращение к оператору при готовом аккаунте.** Оператор указывает тот же телефон и совпадающие ФИО/email. Заявка автоматически связывается с существующим клиентом и видна в его кабинете. Логин и пароль не меняются.

Пример активации кабинета после обращения к оператору:

```json
{
  "FIO": "Иван Петров",
  "number": "+79161234567",
  "email": "ivan@example.com",
  "login": "ivan_p",
  "password": "client-password123",
  "application_code": "AB12CD34"
}
```

Код в примере нужно заменить кодом реальной заявки этого клиента. Форматы телефона нормализуются, регистр кода не важен. ФИО и email должны совпадать с карточкой оператора (без учёта регистра и пробелов по краям).

Регистрация возвращает профиль с HTTP 201; после неё нужно отдельно войти через `/auth/client/login`. Вход устанавливает cookie сессии клиента. Список `/client/applications` и проверка `/client/status?application_code=...` доступны только после входа и только для собственных заявок.

Если телефон уже зарегистрирован, API возвращает 409 и не заменяет пароль. Для карточки без аккаунта отсутствие кода даёт 409; неверные данные или чужой код — 403. Занятый логин также даёт 409, при этом карточка не активируется частично.

Для привязки кабинета используются существующие поля `clients.login`, `clients.password_hash` и связь `applications.client_id`. Для полного текущего API, включая доставку, примените миграции `001`–`004` из раздела настройки БД.

### Онлайн-заявки и доставка в центр

Источник определяет сервер: `/client/applications` создаёт `source: "online"`, а `/operator/add_application` — `source: "offline"`. Клиент и оператор не могут подменить источник полем в запросе. В списках и карточках возвращаются `source` и готовая подпись `source_label` («Онлайн» / «Офлайн»).

Тело `POST /client/applications`:

```json
{
  "info": "Не включается",
  "device": "Ноутбук",
  "device_model": "Lenovo ThinkPad",
  "address": "Москва, ул. Ленина, 1",
  "courier_visit_at": "2026-10-25T14:30:00+03:00"
}
```

`courier_visit_at` — желаемое время встречи. Поле обязательно только для онлайн-создания: дата должна быть в будущем и содержать часовой пояс. Сервер сохраняет момент времени в UTC; фронт отображает его в местном времени. Пропуск поля, прошедшее время и время без часового пояса возвращают 422. Адрес и данные устройства остаются обязательными.

До ремонта онлайн-заявка проходит этапы, которыми управляет оператор:

| `delivery_status` | `status_info` | Статус для человека | Следующее действие оператора |
| --- | ---: | --- | --- |
| `created` | -3 | Заявка создана | Курьер выехал |
| `courier_dispatched` | -2 | Курьер выехал | Подтвердить получение посылки курьером |
| `courier_picked_up` | -1 | Курьер забрал посылку | Подтвердить прибытие в ремонтный центр |
| `arrived` | 0 и выше | Посылка прибыла в ремонтный центр, затем статусы ремонта | Доставка завершена |

Значения прежних этапов ремонта `0`–`4` сохранены. Прибытие переводит заявку на этап `0`, после чего инженер может взять её на диагностику. До прибытия диагностика, ремонт и выдача запрещены. Офлайн-заявки сразу создаются на этапе `0`, без курьерских этапов и времени встречи.

Для переключения оператор отправляет `POST /operator/{application_id}/delivery` с телом `{"status": "courier_dispatched"}`, затем `{"status": "courier_picked_up"}`, затем `{"status": "arrived"}`. Нужен Bearer-токен оператора. Пропуск, повтор или откат этапа возвращает 409, неправильный формат — 422, офлайн-заявка — 400, отсутствующая заявка — 404. Другие роли получают 403, запрос без токена — 401.

Ответы сотрудникам содержат `next_delivery_status` и `next_delivery_action`: фронт может показать одну кнопку следующего действия и передать её целевой статус. После прибытия оба поля равны `null`. Это защищает от случайного выбора неподходящего статуса и двойного нажатия; параллельные запросы обрабатываются с блокировкой строки заявки.

`GET /operator/deliveries` возвращает ещё не прибывшие онлайн-заявки, сначала с самой ранней встречей. Фильтр `?status=created`, `courier_dispatched` или `courier_picked_up` выбирает отдельный этап. `?status=arrived` показывает онлайн-заявки, уже поступившие в центр, включая последующие этапы ремонта. Адрес и время встречи доступны оператору в каждом элементе списка.

В кабинете клиента `/client/applications` возвращает источник, `courier_visit_at`, `delivery_status` и актуальные статусы только его заявок. Повторная диагностика после неудачной проверки ремонта не запускает доставку заново.

## 📊 Основные сущности

### Application

Заявка клиента:

* клиент (`client_id`); ФИО, телефон и email в ответах API берутся из клиента
* описание проблемы
* статус ремонта
* источник (`source`): `online`, `offline` или `unknown` у старых заявок; удобное время встречи с курьером (`courier_visit_at`)
* этап выполнения (`status_info`): -3 — создана онлайн, -2 — курьер выехал, -1 — посылка у курьера, 0 — в центре / ожидание диагностики, 1 — диагностика завершена, 2 — ремонт завершён, 3 — проверка пройдена, 4 — выдана клиенту
* результат диагностики и комментарий последней проверки (`check_result`)
* инженер, забронировавший заявку (assignee_engineer_id), и мастер, взявший её в ремонт (assignee_repairer_id)
* список запчастей, стоимость запчастей, стоимость работы и итоговая стоимость

---

### Client

Клиент сервисного центра, один на телефон:

* ФИО
* телефон (уникальный)
* email
* все его заявки

---

### StockPart

Позиция на общем складе (ведёт админ):

* название (уникальное)
* цена
* остаток

---

### Part

Запчасть, списанная со склада на заявку:

* привязка к заявке и к позиции склада
* название и цена на момент списания (изменение цены на складе не меняет уже идущие ремонты)
* количество

---

### AccessCode

Данные доступа сотрудников:

* ФИО
* роль
* хеш кода
* активность аккаунта

## 🔄 Жизненный цикл заявки

```
Создание онлайн-заявки
        |
        v
Курьер выехал (оператор)
        |
        v
Курьер забрал посылку (оператор)
        |
        v
Посылка прибыла в ремонтный центр (оператор)
        |
        v
Ожидание диагностики <---- Создание офлайн-заявки оператором
        |
        v
Взята в диагностику (инженер)
        |
        v
Диагностика завершена
        |
        v
Взята в работу (мастер)
        |
        v
Ремонт выполнен
        |
        v
Проверка (инженер заявки) ---- не пройдена ----> Ожидание повторной диагностики
        |
        v
Проверка пройдена
        |
        v
Выдано клиенту (оператор), заявка закрыта
```

До завершения своего этапа инженер или мастер может отказаться от заявки, а оператор может снять исполнителя. Тогда заявка возвращается на ожидание своего этапа, и её берёт другой сотрудник.

## ✅ Тесты

Из корня проекта с активированным окружением:

```bash
cd backend
python -m pytest
```

Тесты используют отдельную SQLite-базу в памяти, рабочую БД из `backend/.env` не трогают.

Прогнать те же тесты на PostgreSQL можно через `TEST_DATABASE_URL`. Указывать **только отдельную пустую БД**: тесты удаляют в ней все таблицы.

```bash
TEST_DATABASE_URL=postgresql://user:password@localhost:5432/repair_test python -m pytest
```
